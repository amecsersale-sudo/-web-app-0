Deploy ให้ใช้งานจริง + สรุปคอร์ส

ใช้เวลาทำประมาณ 20-30 นาที · บทสุดท้ายของหลักสูตร "สอนทำ Web App ตั้งแต่ 0"

เป้าหมาย · สร้างระบบเงินเดือน/ความปลอดภัยใช้เองที่ ESS

แอปทำงานสมบูรณ์แล้วบนเครื่องตัวเอง (localhost) แต่เพื่อนร่วมงานที่ ESS ยังเข้าไม่ได้เพราะ localhost หมายถึง "เครื่องนี้เท่านั้น" บทสุดท้ายนี้จะพาเลือกทางที่เหมาะกับงานจริง แล้วสรุปภาพรวมทั้งหลักสูตร

1. ทำไมไม่ใช้ Cloudflare Pages ตรงๆ

ตอนต้นคอร์สเคยพูดถึง Cloudflare — ข้อควรรู้คือ Cloudflare Pages ถูกออกแบบมาสำหรับเว็บที่เป็นไฟล์ static (HTML/CSS/JS ล้วนๆ ไม่มี server ประมวลผลต่อเนื่อง) ส่วนแอปของเราต้องมี Express รันตลอดเวลา และมีไฟล์ฐานข้อมูล SQLite ที่ต้องเก็บถาวร ซึ่งไม่ตรงกับรูปแบบที่ Cloudflare Pages ทำได้ตรงๆ (มีทางเลือกขั้นสูงกว่าคือ Cloudflare Workers + D1 แต่ต้องปรับโค้ดพอสมควร ไว้เป็นบทต่อยอดในอนาคต)

2. ตัวเลือกที่เหมาะกับแอปแบบนี้

ตัวเลือก A — รันบนเครื่อง/เซิร์ฟเวอร์ในบริษัท (แนะนำสำหรับข้อมูลอ่อนไหว)

สำหรับระบบที่มีข้อมูลพนักงาน/เงินเดือน วิธีที่ปลอดภัยและง่ายที่สุดคือรันบนเครื่องหรือเซิร์ฟเวอร์ ที่อยู่ในเครือข่ายภายในบริษัท (LAN) ไม่ต้องเปิดออกอินเทอร์เน็ตสาธารณะเลย — เพื่อนร่วมงานเข้าผ่าน IP เครื่อง เช่น http://192.168.1.50:3000 ได้จากคอมในออฟฟิศเดียวกัน ข้อดีคือควบคุมความปลอดภัยได้เต็มที่ ไม่มีค่าใช้จ่ายรายเดือน เหมาะกับข้อมูลเงินเดือนที่สุด

ตัวเลือก B — Railway (ถ้าต้องเข้าถึงได้จากนอกบริษัทด้วย)

Railway รองรับ persistent volume สำหรับเก็บไฟล์อย่าง reports.db ได้จริง และรองรับ Node.js โดยตรง เริ่มต้นมีเครดิตทดลองใช้ฟรี ก่อนเข้าสู่การคิดค่าใช้จ่ายตามการใช้งานจริง (usage-based) เหมาะถ้าต้องการให้เข้าถึงได้จากทุกที่จริงๆ

ตัวเลือก C — Render (ต้องอัปเกรดแผนเพื่อเก็บข้อมูลถาวร)

Render ใช้งานง่ายคล้าย Railway แต่ตามเอกสารทางการของ Render เอง แผนฟรีมี filesystem แบบชั่วคราว (ไฟล์หายทุกครั้งที่ redeploy) — ถ้าจะเก็บ reports.db ถาวรจริง ต้องอัปเกรดเป็นแผนเสียเงินที่รองรับ persistent disk

สรุปคำแนะนำสำหรับ ESS

ถ้าระบบนี้มีแค่คนในบริษัทใช้ — ตัวเลือก A (รันในเครือข่ายภายใน) คุ้มค่าที่สุดทั้งด้านความปลอดภัย และไม่มีค่าใช้จ่าย ถ้าจำเป็นต้องให้พนักงานเข้าจากนอกบริษัท (เช่น ทำงานจากบ้าน) ค่อยพิจารณา Railway แล้วเพิ่มระบบล็อกอินก่อนเปิดใช้งานจริงเสมอ — ยินดีช่วยดูรายละเอียดเพิ่มถ้าต้องการเจาะจงขึ้น

3. ขั้นตอน deploy แบบย่อ (ตัวเลือก B/C)

  1. สร้างบัญชี GitHub (ถ้ายังไม่มี) แล้ว push โค้ดทั้งโปรเจกต์ขึ้น repository
  2. สมัครบัญชี Railway หรือ Render แล้วเชื่อมกับ GitHub repo นั้น
  3. ตั้งค่า build command: npm install
  4. ตั้งค่า start command: node server.js
  5. ถ้าใช้ Railway: เพิ่ม Volume แล้ว mount ไปที่โฟลเดอร์ที่เก็บ reports.db
  6. กด deploy — ได้ URL สาธารณะกลับมา (เช่น https://ess-safety-app.up.railway.app)

4. ข้อควรระวังก่อนใช้งานจริงกับข้อมูลบริษัท

  • ห้ามเปิดสาธารณะโดยไม่มีการล็อกอิน ถ้าเป็นข้อมูลเงินเดือนหรือข้อมูลส่วนบุคคลของพนักงาน
  • เพิ่มระบบยืนยันตัวตนอย่างน้อยแบบง่าย (เช่น รหัสผ่านเดียวกันทั้งทีม หรือ login ด้วยอีเมลบริษัท) ก่อนเปิดใช้จริง
  • สำรองไฟล์ reports.db เป็นระยะ (copy ไฟล์ไปเก็บที่อื่นด้วย) เผื่อเซิร์ฟเวอร์มีปัญหา
  • ถ้าข้อมูลอ่อนไหวมาก (เงินเดือน) ให้เลือกตัวเลือก A (เครือข่ายภายใน) เป็นอันดับแรกเสมอ

แหล่งอ้างอิงหลัก

Render FAQ — ข้อมูล free tier และ persistent disk และเอกสารเริ่มต้นใช้งานของ Railway

สรุปเส้นทางทั้งหลักสูตร

แผนภาพ 6 — เส้นทางทั้ง 9 บทของหลักสูตรนี้

จากบทที่ 1 ที่ยังไม่รู้ว่า frontend/backend/database ต่างกันอย่างไร มาถึงตอนนี้มีระบบแจ้งเหตุความปลอดภัย ที่ทำงานครบวงจรจริง เขียนเองทุกบรรทัด เข้าใจว่าทำไมแต่ละส่วนถึงต้องมีอยู่ — นี่คือรากฐานเดียวกับที่ใช้สร้าง ระบบเงินเดือนหรือเครื่องมือ internal อื่นๆ ที่ ESS ได้เลย โครงสร้างจะคล้ายกันมาก (ฟอร์ม → validate → backend → เก็บ database → แสดงผล)

ไปต่อจากนี้ได้อย่างไร

  • ลองสร้างโปรเจกต์ที่ 2 เอง เช่น ระบบเช็กสลิปเงินเดือน — โครงสร้างจะคล้ายที่เรียนมาทั้งหมด
  • เพิ่มระบบล็อกอิน (authentication) ก่อนเอาไปใช้กับข้อมูลจริง — เป็นหัวข้อที่ควรเรียนต่อโดยตรง
  • เรียนรู้ framework อย่าง React เมื่อแอปเริ่มซับซ้อนขึ้นมาก (ตอนนี้ยังไม่จำเป็น)
  • กลับไปดูบทเรียนเก่าๆ ได้ตลอดเวลาที่ต้องการทบทวน — เก็บไฟล์ทั้งหมดไว้ดีๆ

ยินดีเรียนต่อได้เสมอ

จบคอร์สนี้แล้วไม่ได้แปลว่าเรียนจบเรื่องเว็บทั้งหมด — ถ้าอยากลงลึกเรื่องไหนต่อ (authentication, React, หรือกลับไปลองเรื่อง Cloudflare ที่พักไว้ตอนต้น) ถามได้เลยทุกเมื่อ
